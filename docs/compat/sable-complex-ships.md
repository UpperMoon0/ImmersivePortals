# Complex assembled Sable ship regression

This development-only suite extends the existing six-block rider E2E; it does not replace it.
Run `python tools/verify.py ships` with Java 21 and a graphical desktop or Xvfb.
Only run the harness in a disposable checkout: its server/client worlds and results are fresh each run.

Use `python tools/verify.py ships --ship-size control` or `--ship-size large` to run one size independently; the default `--ship-size all` runs both. Each selected baseline size requires ordinary and dimension-stack routes with four legs each, plus its vertical broadside outbound/return route with two legs. The same option works with `ships-aeronautics`, where each size requires its powered ordinary route. Separate sizes use separate server/client directories, fresh worlds, processes, result directories and summary records, so a control failure cannot prevent a large-size CI job from running or be hidden by its success. Baseline CI runs all four UDP/TCP × control/large jobs with fail-fast disabled.

When the changes filter selects E2E, **Required verification requires all six configured ship jobs**: four baseline UDP/TCP × size rows and two Aeronautics UDP × size rows. A failed, cancelled or unexpectedly skipped ship matrix blocks the aggregate check. Aeronautics remains an optional runtime feature, but its configured CI rows are mandatory and fail if dependency staging or any probe fails. When the changes filter explicitly selects no E2E, the aggregate instead requires every heavy matrix, including ships, to be skipped. Existing rider and renderer gates remain required.

Release verification has the same six mandatory ship rows when running fresh. Reused CI evidence must contain all 47 exact required jobs, including these six ship jobs, successful on the same tagged commit and run attempt. The release publication gate accepts skipped fresh ship jobs only after that complete reused evidence is validated; absent or failed ship evidence cannot bypass verification.

Reuse policy is loaded from the executing workflow commit, separately from the requested tag. An older tag's smaller historical CI contract cannot authorize skipping current required jobs. Its evidence must meet the executing workflow's contract or fresh verification runs; tags too old to support those checks fail closed. Artifact commit, run attempt and checksum remain bound to the requested tag.

For example, `ships --ship-size large` writes `build/sable-ship-flight-large-e2e/` and `build/verification-ships-large.json`, using `run-sable-ship-flight-large-server/` and `run-sable-ship-flight-large-client/`. Powered paths additionally include `-aeronautics` before the size. Runs without a size filter retain the original evidence directory names and use their own mode-specific server/client directories.

Ship modes use a 10-chunk client render distance and server view distance so the large-vessel overview camera is inside the visible range. Both simulation distances remain 3; the 854×480 framebuffer, 60 FPS cap, timeouts and pixel thresholds are unchanged. Existing rider E2E and smoke modes retain their 3-chunk view/render distance.

## Scope

- A 176-block 7×5×11 control and a 4,185-block 49×17×65 large ship, genuinely placed in a server world and moved into a Sable sublevel by `SubLevelAssemblyHelper.assembleBlocks`.
- The large fixture must contain at least 3,500 blocks, occupy at least 12 actual plot chunks, and occupy more vertical sections than horizontal chunks. Dimensions are fixed, not inferred from a tiny sparse surrogate.
- Continuous hull/deck, longitudinal spine, ribs, glass canopy, distinct extremity markers, two powered Create motor/shaft/cog drive trains, a real Create seat and player, two loaded barrels and a loaded item drain.
- Ordinary finite portals and dimension-stack boundaries, with 90-degree yaw transforms and four alternating crossings per size/route, plus two vertical broadside crossings per size (six cases / 20 crossings total).
- Real native rigid-body flight: launch velocity is set once; subsequent native physics ticks carry the assembled vessel through the seam. At least five native flight ticks and eight meters of pre-seam travel are required. Observation barriers use velocity-feedback stationkeeping, never vessel teleportation.
- At each handoff: original UUID only in the destination, retained seat/passenger graph, full block and block-entity manifest, exact cargo inventory, velocity and orientation continuity.
- After each handoff: reverse motor speed, toggle a lever and its normally scheduled lamp, remove/restore a block, and switch a contrasting panel. The real client verifies the complete multi-chunk state, every kinetic speed, unique ownership and passenger relation before acknowledgment. Framebuffer pixels must show the requested panel color; every phase saves a PNG.

Reports are `build/sable-ship-flight-e2e/server-ships.json` and `client-ships.json`. The harness validates the exact case/leg set, matching ship identities, nonvacuous fixture and flight sizes, affirmative invariants, actual screenshot files and the existing critical-error log checks. Dedicated UDP/TCP CI lanes preserve reports, screenshots, configs, logs and crash reports even on failure.

## Important limits

The fixture is an actual assembled Sable vessel with native physics and functional Create machinery. Its launch/hover controller is explicit test input. The motors do not generate aerodynamic lift. The pinned optional lane below tests wooden propellers; it does **not** certify balloons, burners, analog controls, fuel consumption or every aerodynamic configuration. The public report about stale burner/lever graphics and a balloon remaining behind at a dimension-stack seam is a motivation, not a reproduced diagnosis.

Panel pixels exercise live block-remeshing; exact lever/lamp/removed-block client states are checked separately. These assertions do not by themselves certify each block's animation or every viewing angle, shader, rendering backend, nested portal, or an unseated walking passenger. Two transport lanes use the pinned baseline runtime, not all networking versions or impairment profiles. Existing renderer and rider-lifecycle suites remain independently required.

## Optional genuine Aeronautics propulsion

`python tools/verify.py ships-aeronautics` stages the official Create Aeronautics 1.3.1 bundle from Modrinth version `Vzp221Un`, SHA-256 `b531dbe1081ee354f6e47ba4e0443b9caa648dfb8c82013a591a20836245bd84`. It contains Aeronautics, Simulated and Offroad 1.3.1; no duplicate Sable or Veil. Source release pin: `d3007b79b8e571fbb2cbaf91f2269869f864d711`. Download and staged copies are size/hash checked; provenance is recorded. Owned addon files are removed after both processes stop; baseline runs reject leftovers. The bundled LICENSE.md distinguishes MIT code from all-rights-reserved assets. This repository downloads the unchanged official release for tests and does not vendor or publish the addon jar/assets; CI uploads test receipts and screenshots only.

This mode adds eight real motor/shaft/wooden-propeller engines to CONTROL (189 blocks), and 252 to LARGE (4,941 blocks). Only ordinary Create RPM controls are written during powered travel; Aeronautics actors apply actual native thrust. Both sides verify addon versions, propeller block entities, kinetic speeds and thrust. Server evidence requires native acceleration and displacement during intervals with no direct velocity/force/pose writes. Upward legs prove movement against gravity. Velocity-feedback observation holds remain explicitly outside these powered intervals.

Powered mode has **two ordinary-portal cases / eight crossings**; the baseline requires six cases / twenty crossings including dimension stacks and vertical broadside flight. The lower powered route uses Overworld origin y32 and portal y-8 to Nether portal y48. Native atmospheric configuration is unchanged. Sable's air-pressure curve reaches zero at the Nether logical ceiling, so the high baseline route and an arbitrary powered stack return are not valid propulsion controls. Actual mass, gravity, pressure and trimmed lift budget must pass before release. An additive UDP addon CI lane is draft until genuine runtime evidence passes.

The framebuffer target has blue and yellow flanking columns and a red/lime mutable center. All three colors, substantial coverage and rejection of stale opposite-color pixels are mandatory; bare red Nether background is insufficient.
